# 2026-09-18

## Fix checkpointing a restored HAMi container ("has unreachable sharing")

### Context
Checkpoint -> restore -> checkpoint failed on the second checkpoint with
`Error (criu/mount.c:1092): mnt: Mount <id> ./usr/local/vgpu/containers/<old-UUID>_trainer
(master_id: 1 shared_id: 0) has unreachable sharing. Try --enable-external-masters.`
The failure is in the dump, not in the restore: the kubelet log shows it coming
back from `CheckpointContainer` and the quoted `dump.log`, while the restore of
the same container finished with `Restore finished successfully`.

Root cause, established from the node's CRIU log, the checkpoint images and the
CRIU sources (v4.2, gitid 309f4289b):

- CRIU restores every mount at the path recorded in the checkpoint and only
  redirects its source. `/tmp/criu.log` of the restore shows
  `Will mount 19539 from .../3f810a04-..._trainer (E)` followed by
  `Will mount 19539 @ ... .../7c1161f3-..._trainer`, so the restored container
  keeps the vGPU directory at the checkpointed path.
- The restored container's `config.json`, however, carried the freshly
  allocated path as the bind destination, because `buildContainerConfig` reuses
  the CDI devices of the restore request and CDI injects the mount HAMi created
  for this pod.
- The OCI runtime derives CRIU's external-mount keys from those destinations,
  and CRIU looks them up by mountpoint (`try_resolve_ext_mount` ->
  `ext_mount_lookup(ns_mountpoint)`). The key therefore never matched, the mount
  was not marked external, and since it is a slave of a peer group outside the
  container (`master_id: 1`), `can_receive_master_from_external()` found no
  candidate and the dump aborted.
- `--enable-external-masters` does not help: `opts.enable_external_masters` is
  only consulted in `resolve_external_mounts()` under `--ext-mount-map auto`;
  the branch that raises the error does not look at it.
- A second, independent defect kept the node's own CRIU configuration from
  covering this: CRI-O wrote `criu-restore.conf` into the checkpoint directory,
  put its path into the `org.criu.config` annotation and then deleted the file.
  The annotation lives on in the container's runtime state, so at the next
  checkpoint the runtime handed CRIU a path that no longer resolved
  (`parse_config()` returns NULL silently) instead of falling back to
  `/etc/criu/runc.conf`. Evidence: every checkpoint of a fresh container has an
  empty `dump.log` (the node config redirects the log), while both checkpoints
  of restored containers have a populated one and no `Parsing config file` line.

### Changes (internal/lib/restore.go)
- Added the `hamiVGPUMount` type pairing the checkpointed mountpoint with the
  host directory of the current run.
- `extractHAMiVGPUSources` -> `extractHAMiVGPUDestinations`: the HAMi mounts are
  now selected by destination. The destination is the only value that matches
  the mountpoint of a checkpoint taken from an already restored container.
  `readHAMiVGPUSourcesFrom{Image,Archive}` renamed accordingly.
- Added `alignHAMiVGPUMounts`, which rewrites the destination of the vGPU mounts
  in the restored spec back to the checkpointed mountpoint while keeping the
  host directory of this run as their source, and returns the resulting pairs.
  Pairing is by container-name suffix with a positional fallback, and the
  operation is idempotent so kubelet retries keep producing the same mapping.
- Added `rewriteHAMiVGPUEnv`, which points the environment variables HAMi
  injects for this run (`CUDA_DEVICE_MEMORY_SHARED_CACHE`) at the same
  mountpoint, so processes exec'ed into the restored container do not look for
  the vGPU cache below a path that is not mounted.
- `buildHAMiExtMountMapLines` now consumes the pairs instead of re-deriving
  them; `writeDeviceRestoreMetadata` takes `[]hamiVGPUMount`.
- The CRIU configuration file moved from the checkpoint directory (removed
  right after a restore) to the container directory, and is no longer deleted
  but rewritten by `cleanupDeviceRestoreMetadata` with the dump-only options
  returned by the new `buildCheckpointCRIUConfig` (`ghost-limit`). The
  restore-only action script, the log redirection and the previous run's
  ext-mount-map entries must not survive into a checkpoint, where an
  ext-mount-map key is the mountpoint and its value is what CRIU writes into
  the image. Renamed to `criu.conf` as it now serves both directions.

### Tests (internal/lib/restore_internal_test.go)
- `extractHAMiVGPUDestinations`: claims layout, legacy containers layout,
  custom prefix, and the regression case where source and destination differ.
- `alignHAMiVGPUMounts`: destination rewrite with the source kept and unrelated
  mounts untouched, idempotency across retries, pairing by container name with
  several vGPU mounts, cross-layout positional pairing, and the two cases where
  nothing can be paired.
- `buildHAMiExtMountMapLines` for the new signature, `rewriteHAMiVGPUEnv`
  including a spec without a process section, and `buildCheckpointCRIUConfig`
  asserting that no restore-only option leaks into a checkpoint.

### Verification
- `go build -tags test ./...`, `go vet -tags test ./internal/lib/` and
  `go test -tags test ./internal/lib/` pass (19 specs in the internal test file).
- `go test -tags test ./internal/...` shows only the two pre-existing failures
  in `internal/factory/container` (`SpecInjectCDIDevices`), which reproduce
  unchanged with the change stashed; they come from the test environment not
  being able to read `/var/run/cdi`.

### Note
Checkpoints taken by the previous code from an already restored container can
carry two vGPU mounts (the checkpointed one and the CDI-injected one). Both are
returned as checkpointed destinations and only the first is paired; the mount
table of those images decides which one is right, and it is not read here. New
checkpoints have exactly one vGPU mount, so this only affects images taken
before this change. Containers restored before this change also keep an
`org.criu.config` annotation pointing at the old, deleted path until they are
recreated.
