# 2026-08-18

## Fix second checkpoint/restore cycle failing in CRIU on device mounts

### Context
A container could be checkpointed and restored once, but checkpointing the
restored container and restoring it again failed inside CRIU with
"No mapping for <id>:<path> mountpoint" on a device such as
`/dev/nvidia-modeset`.

Root cause: the post-restore CRIU action script bind-mounted every device onto
its own container path after creating the node with `mknod`. The whole block
runs inside the container's mount namespace via `nsenter -m`, so the bind
source resolves inside the container as well; the bind changed nothing but left
one extra mount entry per device in the container's mount table.

Evidence collected from checkpoints on the node (`crit decode` of
`mountpoints-*.img`):
- checkpoints of freshly created containers list only `/dev`, `/dev/pts`,
  `/dev/mqueue`, `/dev/shm`, `/dev/termination-log` under `/dev`;
- a checkpoint of a restored container additionally lists `/dev/nvidia-modeset`,
  `/dev/nvidia-uvm`, `/dev/nvidia-uvm-tools`, `/dev/nvidiactl`, `/dev/nvidiaN`,
  `/dev/dri/cardN`, `/dev/dri/renderDN`.

Those extra mounts are dumped by the following checkpoint and CRIU cannot
restore them: they are external mounts with no `ext-mount-map` entry, since
CRI-O only emitted such entries for HAMi vGPU directories and runc only maps
mounts present in `config.json`. The bind was also unnecessary: CRIU dumps the
container's `/dev` tmpfs including the device nodes, and the script's `mknod`
already covers a changed major:minor on the restore node.

### Changes
- `contrib/criu-device-restorer/criu-device-restorer.sh`
  - Removed the `mount --bind` of each device; the script now only recreates
    the device node (`mknod` + `chmod`) inside the container's mount namespace.
  - Added `set -e` to the nsenter'd shell and dropped the `2>/dev/null || true`
    masking on `mknod`/`chmod`, so a failing node creation is reported instead
    of being silently swallowed.
  - Updated comments and log messages to describe node restore rather than
    remounting.
- `internal/lib/restore.go`
  - Added `buildDeviceExtMountMapLines`, emitting one
    `ext-mount-map <path>:<path>` line per device, so checkpoints already taken
    from a container restored by the previous script version still restore.
  - `writeDeviceRestoreMetadata` now builds the device mappings first, appends
    the device `ext-mount-map` lines to the HAMi ones, and skips writing
    `device-mapping.json` when the action script is absent while still writing
    the CRIU config with the mapping lines.
- `internal/lib/restore_internal_test.go`
  - Tests for `buildDeviceExtMountMapLines`: line format, deduplication and
    empty-path skipping, and the no-device case.

### Verification
- `go test -tags test ./internal/lib/` passes.
- Ran the old and new script against the same throwaway mount namespace with a
  synthetic `device-mapping.json`: the old script left two extra bind mounts,
  the new one leaves none while creating both device nodes with the expected
  major:minor.

## Stop carrying GPU device nodes of the previous run over on restore

### Context
`buildContainerConfig` rebuilt the device list of a restored container purely
from the checkpoint's `spec.dump`, skipping only paths prefixed with
`/dev/nvidia` because CDI re-injects them. The DRM nodes belonging to the same
GPU (`/dev/dri/cardN`, `/dev/dri/renderDN`) were not skipped, although the
NVIDIA CDI spec pairs one card and one render node with every GPU
(`containerEdits.deviceNodes` of each device in
`/var/run/cdi/k8s.device-plugin.nvidia.com-gpu.json`). Restoring on a GPU other
than the one the checkpoint was taken on therefore gave the container the DRM
nodes of the old GPU next to the freshly injected ones.

The devices of the restore request (`CreateContainerRequest.config.devices`)
were dropped entirely, so a non-CDI plugin allocation for the new run was
ignored as well.

### Changes (server/checkpoint_utils.go)
- Added `buildRestoreDevices`: the devices of the restore request win, and the
  checkpoint only contributes devices the request does not mention and that CDI
  does not manage, so unrelated devices (for example `/dev/fuse`) still survive
  a restore.
- Added `cdiManagedDevicePrefixes` (`/dev/nvidia`, `/dev/dri/`) and
  `isCDIManagedDevice`, replacing the inline `/dev/nvidia` prefix check.
- `buildContainerConfig` now calls `buildRestoreDevices` outside the
  `dumpSpec.Linux != nil` block, so request devices are honoured even for a
  checkpoint without a Linux section.

### Tests (server/checkpoint_utils_test.go, new)
- CDI-managed devices from the checkpoint are dropped while other devices are
  kept.
- Request devices win over the checkpoint's devices.
- A path present in both is not duplicated and keeps the request's permissions.
- A `spec.Spec` without a Linux section returns the request devices.

### Verification
- `go test -tags test ./server/ -run TestBuildRestoreDevices` passes.
- The full `./server/` suite fails in the same three pre-existing
  `ContainerRestore from archive into new pod` specs before and after the
  change (verified by stashing the change and re-running).

### Note
Restores that never resolve any CDI device (legacy NVIDIA hook mode, where
`NVIDIA_VISIBLE_DEVICES` holds bare GPU UUIDs) now lose the DRM nodes as well,
matching the NVIDIA device nodes they already lost. Such setups need the device
plugin in CDI mode, or the devices passed in the restore request.
