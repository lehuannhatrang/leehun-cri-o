# 2026-10-22

## Point exec'ed processes of a restored HAMi container at the checkpointed shared region

Branch: `2026-10-22/hami-shared-cache-env` (from `cc844737c`).

### Context
After a restore, processes started with `kubectl exec` segfaulted as soon as
they initialised CUDA/NVML (`Fail to open shrreg .../<new pod UID>_kernel/<new uuid>.cache: errno=2`),
while the restored process tree kept working. The two sets of processes looked
at different `CUDA_DEVICE_MEMORY_SHARED_CACHE` values: the restored ones carry
the checkpointed path, exec'ed ones the path CDI injected for the new pod,
which is not mounted in the restored container.

Two causes:

- `rewriteHAMiVGPUEnv` only moved the directory part to the checkpointed
  mountpoint. HAMi also names the cache FILE after a per-pod UUID, so exec'ed
  processes would have opened a second region next to the restored one, with
  separate accounting.
- `ContainerRestore` wrote the remapped spec to `config.json` but never updated
  the container's in-memory spec, and `ExecContainer` builds the exec process
  from `c.Spec().Process`. None of the HAMi env rewriting reached exec'ed
  processes until the next CRI-O restart reloaded the container from disk.

### Changes (`internal/lib/restore.go`)
- `readCheckpointSpecFromImage` / `readCheckpointSpecFromArchive` (renamed from
  `readHAMiVGPUDestinationsFrom*`) return the checkpointed spec; the caller
  extracts both the vGPU mountpoints and the shared-region path from it.
- `extractHAMiSharedCache` reads `CUDA_DEVICE_MEMORY_SHARED_CACHE` from the
  checkpointed spec.
- `restoreHAMiSharedCacheEnv` sets that variable in the restored spec to the
  checkpointed value, only when its directory is one of the restored HAMi
  mountpoints. The memory and SM limits are left as CDI injected them, so
  exec'ed processes carry the limits of the current allocation.
- `syncExecEnv` copies the restored process environment into the in-memory
  spec after `config.json` is saved.

Unit tests added in `internal/lib/restore_internal_test.go`.

### Verified on gpu-1 with FluidCR examples/normal-terminal
Seed with a plain `kubectl exec ... nvidia-smi` before `fluidcr-ctrl resume --all`,
no symlinks:

| Run | Claim | Exec env path == pid 1 | nvidia-smi | Shared region | Exec alloc probe |
|---|---|---|---|---|---|
| gen0 | 8192 MiB / 30 | yes | - | 8192 / 30 | - |
| gen1, same claim | 8192 / 30 | yes | exit 0, 8192 MiB | one file, 8192 / 30 | 4.0 GiB + worker 3.59 GiB |
| gen1, other claim | 16384 / 40 | yes | exit 0, 16384 MiB | one file, 16384 / 40 | 12.0 GiB + worker 3.59 GiB |
| gen2 (from gen1 16384/40) | 8192 / 30 | yes | exit 0, 8192 MiB | one file, 8192 / 30 | 4.0 GiB + worker 3.59 GiB |
| gen2 in-place pause/resume | 8192 / 30 | yes | not needed | same inode, 8192 / 30 | - |
| gen3 (from gen2) | 8192 / 30 | yes | exit 0, 8192 MiB | one file, 8192 / 30 | 4.0 GiB + worker 3.59 GiB |

Training resumed from the parked step every time. The worker maps the single
real file in the new host directory, and spec.dump of a restored container
carries the gen-0 path, so the value stays stable across generations.

### Still required outside CRI-O
The region still has to be created (seeded) by an exec'ed process before the
restored worker is resumed; otherwise the worker creates it from its
checkpointed env with the old limits.

## Regression check: non-HAMi workloads on the same build

Installed build: cc844737c plus the changes above (gpu-1 previously ran
9c0ca870b, so cc844737c's restore changes are live there for the first time).
Only `internal/lib/restore.go` differs from 9c0ca870b; the dump path is
unchanged. For a pod without the `hami.io/dra` label the HAMi code is skipped,
and the one change that still applies is `syncExecEnv`, which gives exec'ed
processes the env of the restored `config.json` (what CRI-O already used after
any restart).

Each case: a Python counter started in the container, checkpointed through the
kubelet API, restored as a new pod, then checkpointed and restored once more.

| Workload | gen1 | gen2 (restore of a restore) |
|---|---|---|
| CPU only: `examples/normal-terminal/pod.yaml` (`python:3.11-slim`) | counter same PID, continues 7 -> 10; exec env identical to gen0; no `org.criu.config` | `config.dump` restored=true; counter continues 20 -> 23; exec env identical |
| NVIDIA DRA GPU (`gpu.nvidia.com`, whole V100, runtimeClass `nvidia-cdi`, no HAMi) | counter continues 8 -> 12; exec `torch.ones` on CUDA ok, `nvidia-smi -L` shows the same GPU; exec env identical | counter continues 22 -> 25; CUDA ok; exec env identical |

The CUDA probe ran via exec and exited before each dump; no live CUDA context
was checkpointed.

Unrelated finding: `examples/normal-terminal/pod.yaml` in FluidCR lacks
`GODEBUG=multipathtcp=0`, so its first dump fails with
`inet: Unsupported proto 262` (cnlab-sshd's MPTCP listener) on any CRI-O build.
The test used a copy with that variable added.

## How the HAMi restore code is gated

- `isHAMiPod` (`internal/lib/restore.go`) checks the sandbox label
  `hami.io/dra == "true"`. Manifests do not set it; HAMi's admission webhook
  (`hami-mutatingwebhookconfiguration`) adds it to pods that request
  `nvidia.com/gpu`. Pods allocating through `gpu.nvidia.com` claims do not get
  it. Without the label, `spec.dump` is not read for HAMi and the mount/env
  remap is skipped, so a HAMi pod restored while the webhook is down reverts to
  the exec segfault.
- `alignHAMiVGPUMounts` only touches mounts under `hami_vgpu_mount_prefixes`
  (`/usr/local/vgpu/claims/`, `/usr/local/vgpu/containers/`, set in
  `/etc/crio/crio.conf.d/99-nvidia.conf` on gpu-1).
- `restoreHAMiSharedCacheEnv` only applies when the checkpointed path's
  directory is one of the realigned mountpoints.
- `syncExecEnv` is not gated: it runs for every restored container.

- Steps: `sudo make`, `sudo make install`,
  `sudo nvidia-ctk runtime configure --runtime=crio`, `sudo systemctl restart crio`
  (done twice; the second build added `syncExecEnv`). Running crio started
  15:08:04 KST from the new `/usr/local/bin/crio`.
- `nvidia-ctk` wrote `/etc/crio/conf.d/99-nvidia.toml`; the drop-ins in
  `/etc/crio/crio.conf.d/` were compared with a copy taken before and are unchanged.
  `make install` also rewrote `/etc/crio/crio.conf` and
  `/usr/local/lib/systemd/system/crio.service`.
- Pending: `systemctl show crio` reports `NeedDaemonReload=yes` because the unit
  file changed. `sudo systemctl daemon-reload` reloads it without restarting crio.
- crio runs with `log_level = "error"` on gpu-1 (99-nvidia.conf), so the
  `Infof` lines of the restore path never reach the journal. Inspect the

  behind that build tag).

## Not covered by the tests

  checkpointed on. That is the only case where the device remapping and the

  same device and no `org.criu.config` annotation was set.
